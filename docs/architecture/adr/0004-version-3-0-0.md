# ADR 0004: Version 3.0.0 for the DualPrint rename

- Status: Accepted. The Owner chose 3.0.0 (spec F005, question 2 = A).
- Feature: F005

## Context
F005 adds no features. It does change every external identity: the exe name, the scheduled task, the mutex, the AppUserModelID, the default PDF folder for new printers, the release asset, the download URL and the repo URL. Anyone who scripted against `MultiPrint.exe`, `MultiPrint Watcher` or `…/latest/download/MultiPrint.zip` will break.

## Options
1. **3.0.0** (major): signals a breaking identity change.
2. **2.3.0** (minor): signals no feature change, but hides the broken link and names.

## Decision
3.0.0. Where the version appears:
- `src/Launcher.cs` source literals: `3.0.0.0` (`build.ps1` rewrites them from `-Version` anyway).
- Tag: `v3.0.0`. `release.yml` derives the build version and the release title `DualPrint 3.0.0` from it.
- `tools/site_content.py`: `VERSION = "3.0.0"` (AC-5.6).
- `CHANGELOG.md`: new `## 3.0.0` entry (tech-writer); entries for 2.2.5 and earlier stay unchanged.
- The app's Settings footer reads the running exe's file version (`DualPrint 3.0.0`), so it is no longer hard-coded (AC-4.4).

## Consequences
- The upgrade logic does **not** compare versions. It detects legacy installs by task name, command line and mutex (ADR 0002), so the version number carries no behavior.
- CI builds without a tag still produce `0.0.0.0`. The footer then shows `DualPrint 0.0.0`, which is acceptable for test builds.
- The next releases are 3.0.x / 3.x.
